# 需求文档

## 🚀 高性能微服务网关系统需求文档 (PRD)

## 1. 项目概述

## 1.1 建设背景
在现代微服务架构中，API 网关作为整个系统的流量总入口，承载着数万甚至数十万的并发 QPS。传统网关在面临路由规则动态频繁变更、多插件（鉴权、限流、日志）流水线流转时，常因为读写锁竞争（Lock Competition）和内存频繁分配触发垃圾回收（GC Garbages）导致系统出现服务抖动（Tail Latency）。
## 1.2 建设目标
基于 Go 官方标准库核心组件 net/http/httputil.ReverseProxy，通过重新设计外壳与扩展机制，构建一款面向企业级、具备极致性能的微服务网关。

* 网络与转发层：100% 继承官方标准库的高可靠性与 HTTP/1.1、HTTP/2 协议支持。
* 路由控制层：实现无锁化（Lock-Free）路由查找，保证动态路由更新时零读请求阻塞。
* 插件扩展层：引入全链路内存池化，实现插件流水线（Plugin Pipeline）执行期间的“零内存分配”（Zero-Allocation）。

## 3. 功能与技术需求 (Functional & Technical Requirements)## 3.1 高性能路由管理组件 (Lock-Free Router)

* 需求描述：网关必须支持动态路由规则更新（如通过 API 动态下发、Consul/Nacos 动态发现），且更新期间不能对高并发下的请求读取造成任何阻塞或延迟上升。
* 技术实现指标：
* 读操作：严禁使用 sync.RWMutex。必须使用 sync/atomic 包的 atomic.Value 进行指针级的原子读取。
   * 写操作：采用 Copy-On-Write（写时复制） 机制。更新路由时，先复制原路由表指针指向的 Map，在副本上完成修改后，通过原子操作（Store）实现指针替换。
   * 路由匹配：支持精确路径匹配，预留前缀匹配（Prefix Matching）与正则匹配的扩展接口。

## 3.2 零拷贝上下文管理 (Zero-Allocation Context)

* 需求描述：网关在处理每个 HTTP 请求时，往往需要在多个插件之间传递上下文数据（如认证后的 UserID、限流指标等）。必须杜绝为每个请求频繁创建临时上下文对象，避免导致高并发下 Go 发生严重 GC 抖动。
* 技术实现指标：
* 池化管理：通过 sync.Pool 建立 GatewayContext 自定义上下文对象池。
   * 生命周期复用：请求进入网关时从 Pool 获取 Context，初始化相关字段；请求完成转发并响应客户端后，必须执行 Reset() 方法清空数据并释放回池中。
   * 内部数据存储：Context 内置的数据中转切片或 Map 必须预分配容量（Pre-allocate），避免动态扩容带来的隐式内存逃逸。

## 3.3 链式插件引擎 (Interceptors & Middleware Pipeline)

* 需求描述：网关需要具备高度扩展性，允许开发者自由编写插件（如安全防护、灰度发布、监控埋点），插件之间呈链式顺序执行，且支持前置拦截和后置处理。
* 技术实现指标：
* 执行设计：仿照洋葱模型（类似 Gin 中间件或 C++ 职责链模式），通过闭包或索引自增驱动 ctx.Next() 递归调用后续插件。
   * 控制截断：任意插件发现异常（如鉴权失败、限流触发），可以通过 ctx.Abort() 立即中断调用链并返回响应。
   * 默认内置插件：
   1. Auth 插件：拦截非授权请求。
      2. RateLimit 插件：基于分布式令牌桶（Token Bucket）的流量整形插件。
      3. Metrics 插件：采集请求耗时、吞吐量及错误率的观测插件。
   
## 3.4 基础反向代理与核心扩展 (Reverse Proxy Kernel)

* 需求描述：底层转发依托官方标准库 httputil.ReverseProxy，但网关外壳需对其核心回调进行拦截与定制化扩展。
* 技术实现指标：
* Director 自定义：重新设计 Director 函数，注入网关重写后的 HTTP Header（如传递 X-Real-IP、X-User-ID 等）。
   * ModifyResponse 自定义：重写此回调，允许后置插件对后端服务返回的 Response Body、Status Code 或 Header 进行无损修改。
   * ErrorHandler 错误处理：重写此回调，捕获后端服务熔断、超时或 502/504 错误，统一转换为企业级标准的 JSON 错误响应，避免暴露后端敏感堆栈。

## 4. 性能考核指标 (Non-Functional Benchmarks)
作为向平台客户交付或展示的作品，系统在完成后需满足以下严苛的跑分及性能指标：

| 考核维度 | 基础标准 | 重构后目标 (Target) | 验证工具/方法 |
|---|---|---|---|
| QPS (吞吐量) | 10,000 req/sec | 25,000+ req/sec (提升 100%+) | wrk -t12 -c400 |
| P99 Latency (延迟) | > 50ms (并发时锁竞争) | < 5ms (长尾延迟保持平稳) | wrk --latency |
| Allocs/Op (单次分配) | > 15 allocs/op | 0-2 allocs/op (趋近于零内存分配) | go test -bench -benchmem |
| GC Pause (垃圾回收停顿) | 有明显波峰 | 趋于平滑直线 | GODEBUG=gctrace=1 |
